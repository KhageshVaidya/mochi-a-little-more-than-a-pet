## Live model measurements (real multi-turn conversations)

Source: `docs/mochi-m1-ollama-benchmark.summary.json` (metrics only), generated by:

```
MOCHI_LIVE=1 MOCHI_BENCH=1 npx vitest run apps/desktop/src/main/mochi-live-ollama.test.ts
```

There are 6 scripts and 16 user turns, each sent after the model's previous reply, through the app's own prompt builder, Ollama streaming and the output guard.

| Model | Replies | Rule violations* | First visible text (median / p90 / max) | Full reply (median / p90 / max) | Reasoning produced |
|---|---|---|---|---|---|
| **qwen3:4b-instruct-2507-q4_K_M** (preferred) | **16 / 16** | **0** | **287 / 379 / 667 ms** | **874 / 1241 / 1268 ms** | 0 chars |
| qwen3:4b (fallback, `think:true`) | 8 / 16 (8 timed out) | 0 in shown replies | 14 227 / 18 303 / 18 303 ms | 14 503 / 18 351 / 18 351 ms | ≈ 620 chars per turn (hidden) |
| qwen3:4b with thinking "disabled" (`think:false` + `/no_think`) | diagnostic only | — | — | 15.9 s for one turn | **Leaks into the reply as untagged text** (the model's planning notes appear in the reply) |

\* Violations checked on every reply: visible reasoning, clinical language, stage directions, more than one question, over 36 words, no reply.

Cold start: the first preferred-model turn after the model was evicted took 2.1–4.8 s. Later turns took about 0.2–0.4 s to the first words. A model switch evicts the other model (the benchmark runs both).

**Conclusion:** the non-thinking instruct build is the right default on this hardware. The `qwen3:4b` fallback is kept, as you asked. It is safe (its reasoning is never shown), but too slow for natural chat (half its turns exceed the 20 s / 30 s limits). Settings states that it is much slower.

The scripts cover a bad day, wanting space, good news, poor sleep, a joke request and a dashboard command. Full transcripts are kept in the project's private research records.

## Limitations and known issues

1. **Reply quality is good, not perfect.** The 4B model still sometimes:
   - gives an odd first reaction ("I know." to "I had a terrible day.");
   - invents small details ("snacks", "the coffee machine");
   - overuses one confirmed memory (chess);
   - leaves a joke's closing quotation mark off.

   The guard enforces the safety and format rules, not taste. Improving this further means prompt work, more style examples in the companion manifest, or a different model.
2. **The fallback model is impractical for chat.** Only 8 of 16 turns finished within the time limits on this Mac.
3. **Cold starts:** the first reply after launch or a model switch can take 2–5 s. Mochi shows a "···" indicator meanwhile.
4. **Opening suggestions stay deterministic.** When there's an approved suggestion, Mochi's first line relays it word for word (Phase 4 guarantee). The model can mention it later, using its exact title.
5. **macOS only verified.** The tray, always-on-top and transparency were tested on macOS arm64 only. Windows is untested on real hardware. (Installers were added in the public-launch milestone; see `docs/RELEASING.md`.)
6. **Not yet implemented:** overlay improvements (all workspaces / full-screen visibility, alpha-mask click-through, crew demo mode with five pets) are Phase B items not in M1. Fable, the dashboard redesign, new artwork and installers were excluded as instructed.
7. **Data location:** the app is branded Mochi, but its user-data folder keeps its pre-rename location until the planned migration.
8. **Anthropic provider:** it works through the same pipeline, but this session had no API key, so it was tested only with a stub (non-streaming).
9. **Internal naming:** internal package names still use the earlier `@orbital/*` scope; user-facing branding is Mochi.
